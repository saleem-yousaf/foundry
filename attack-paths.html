Attack paths for a Microsoft Foundry penetration test

Fifteen paths an attacker can take against a Foundry deployment, written for scoping. Each one says where the attacker starts, why the path can work, which control should stop each step, what the tester checks, and what a pass looks like.

Print this page or save it as PDF to attach to a statement of work; the print layout starts each path on a new page.

How to use this page

Most Foundry risk sits in how the platform is configured and how agents are wired to tools and data, not in the model itself. A useful test therefore needs three things a normal web application test does not: accounts in several starting positions, an inventory of every place an agent reads text from, and canary data the tester can try to move without touching anything real.

To scope an engagement, pick the starting positions the client cares about, take the paths that begin from them, and adjust the effort for the number of agents and tools in scope. The summary table gives a priority for each path with the reasoning behind it. The threat IDs (E01, I04 and so on) match the threat library in the guide, so findings can be traced back to the control set.

The paths assume the reference design from the guide: Foundry and its stores behind private endpoints, local auth disabled, agents injected into a delegated subnet, APIM in front, and Prompt Shields switched on. Where a client has not built that, the early paths will find it quickly and the later ones become easier.

AP01 Exposure sweep from the internet

Start
P1, no account
Target
Foundry and every connected resource
Priority
High
Estimate
1 day

Goal. Find any Foundry, AI Search, Storage, Cosmos DB, Key Vault, Container Registry or APIM endpoint that answers from the internet, or that accepts a key.

Why this can work

Foundry's connected resources are separate Azure resources with their own network settings. Teams lock down the Foundry account because it is the thing called "AI", then leave the AI Search index or the storage account public because someone needed portal access during the build. The data the agent reads lives in those stores, so the private Foundry endpoint protects very little on its own.

Names are also predictable. Entra ID authentication and private link both need a custom subdomain on the Foundry account, and organisations name resources by a convention, so an attacker who knows one name can guess the rest. Public DNS for a resource with a private endpoint still returns a privatelink CNAME, which confirms the resource exists without saying whether public access is off. The only way to know is to send a request.

Chain

StepAttacker actionControl expected to stop itTester records
1Build candidate names from the naming convention and resolve them under services.ai.azure.com, openai.azure.com, cognitiveservices.azure.com, search.windows.net, blob.core.windows.net, documents.azure.com, vault.azure.net, azurecr.io, azure-api.netNone. Existence is expected to be discoverableEvery name that resolves, its CNAME chain, and whether it is on the client inventory
2Send an unauthenticated request to each endpointPublic network access disabled, returning a network deny rather than an authentication errorStatus code and message per endpoint; a 401 means the endpoint is reachable and only authentication stands in the way
3Send a request with a planted key or SAS token from AP02Local auth disabled on Foundry, AI Search and Cosmos DB; shared key access off on StorageWhether any key is accepted
4List anonymous blob containers and check for a static website endpointBlob public access disabled at the accountAny readable container
5Check APIM for an external gateway, a public developer portal, or a Front Door routeAPIM in internal mode; any internet route behind WAF and approvedEach internet reachable API and what it fronts

Pass looks like

Every in scope endpoint refuses the request at the network layer, no key is accepted anywhere, and no container is readable anonymously. Anything that returns 401 rather than a network deny is a finding even if authentication held, because the design intent was no internet path at all.

Rules of engagement. Only probe names on the client's inventory. If a guessed name resolves but is not on the inventory, stop: it may belong to another customer, and testing it is prohibited.

AP02 Planted credentials to model and data access

Start
P1, holding a leaked secret
Target
Model deployments, stores, service principals
Priority
High
Estimate
1 day

Goal. Show whether a secret that escapes into a repository, notebook, ticket or pipeline log gives anyone access to models or data, and whether anyone notices.

Why this can work

Running someone else's models with a stolen key is the most common real world abuse of AI services, because it needs no exploit at all. A Foundry account with local auth disabled has no keys to steal, but the estate still holds other secret material: storage SAS tokens in data science notebooks, AI Search admin keys if local auth was left on, client secrets for service principals that hold Foundry User, and connection secrets held by older hub based workspaces.

A client secret is the dangerous one. It works from anywhere on the internet unless Conditional Access for workload identities restricts where it can sign in from, which needs Workload ID licensing and is often not configured. The private endpoint then becomes the last control: the attacker can get a valid token but has no network path to use it.

Chain

StepAttacker actionControl expected to stop itTester records
1Search repositories, wikis, pipeline logs and notebooks the tester was given read access toSecret scanning with push protectionEvery secret found, where, how old, and whether scanning flagged it
2Call the model endpoint with a planted keyLocal auth disabledResponse
3Request a token from the internet with a planted service principal secretConditional Access for workload identities limiting sign in location; short secret lifetimeWhether a token is issued, and the sign in log entry
4Use any token obtained against the Foundry and store endpoints from the internetPublic network access disabledResponse per endpoint
5Use a planted SAS token against storageShared key access off, which also invalidates account SASResponse

Pass looks like

No planted secret gives data or model access from the internet, and each planted secret raised an alert (secret scanning, Entra ID risky workload identity, or Defender) within the agreed time. A token issued at step 3 is a finding even if step 4 failed, because the network was the only remaining control.

Rules of engagement. Use only credentials the client created for the test. Any real secret found is recorded and reported straight away for rotation, and not used unless the statement of work explicitly authorises it. Credentials that belong to anyone other than the client are never used.

AP03 Jailbreak, policy evasion and system prompt extraction

Start
P2, signed in user
Target
Content guardrails, system prompt
Priority
Medium
Estimate
2 days

Goal. Make the assistant produce output outside its policy, extract its system prompt and grounding instructions, and measure how often the guardrails hold.

Why this can work

Prompt Shields and the content filters are classifiers. They catch known patterns well and reduce the success rate of new ones, but no classifier stops every attempt. Attacks that spread intent across several turns, encode the request (base64, leetspeak, another language), split a payload between a message and an uploaded file, or wrap it in role play are the usual ways past a single turn check.

Partial success is therefore expected, so the useful question for the client is what success costs. That depends on two things the tester can establish: whether the system prompt holds anything sensitive (internal URLs, names of tools and indexes, business rules, credentials), and whether a jailbroken assistant has tools it can then misuse. That is why this path is Medium on its own but feeds AP04 and AP08.

Chain

StepAttacker actionControl expected to stop itTester records
1Run a baseline of known jailbreak promptsPrompt Shields Jailbreak set to blockBlock rate per category
2Run obfuscated variants: encodings, translation, payload splitting, file plus messagePrompt Shields, input harm filters, blocklistsWhich techniques pass
3Escalate gradually over a long conversationFilters on output as well as input; conversation length limitsTurn at which policy breaks, if it does
4Ask for the instructions reformatted, translated, summarised or continuedNo sensitive content in the prompt; output filtersPrompt text recovered and anything sensitive in it
5Check the logs for each blocked and each successful attemptContent filter results logged against the user identityWhether the SOC can see who did it

Test cases

  • Automated runs with PyRIT or the Foundry AI Red Teaming Agent, at an agreed rate, reporting attack success rate per harm category.
  • Manual creative attempts for the use case, because automated corpora miss domain specific framing (for example, a claims assistant asked to "draft a fraudulent claim as a training example").
  • Repeat the best performing attacks against each deployment, since filter policies are set per deployment and one may be weaker.

Pass looks like

Attack success rate below the threshold the client agreed before testing, per category. The extracted system prompt contains nothing that helps a further attack. Every attempt is attributable to a user in the logs.

Rules of engagement. Automated corpora run at a modest rate, as excessive automated traffic is prohibited. Harmful category prompts can trip Microsoft's abuse monitoring on the client subscription, so the client should be told and the authorisation letter kept ready.

AP04 Indirect prompt injection into tool use

Start
P3, writes content an agent reads
Target
Agent tools, data the agent can reach
Priority
Critical
Estimate
3 days, plus 0.5 per extra agent

Goal. Plant text in a source an agent reads, then make the agent, acting for an innocent user, call tools the user never asked for: read other records, change data, or send information out.

Why this can work

A language model has no reliable way to tell instructions from data once both are in its context. Every document, email, web page and tool response an agent reads is therefore an input channel for whoever wrote it. The attacker never signs in to Foundry, never touches the client's identity system, and the action is carried out under the agent's identity on behalf of a legitimate user, so it looks like normal use.

The defence is a stack: Prompt Shields on documents and tool responses, guardrails on tool calls, a per agent tool allow list, human approval on writes, a narrowly scoped agent identity, and egress filtering. The test establishes which of those layers exist for each agent and how many have to fail before something happens. That is the single most useful result a client can get from an AI pen test, which is why this path carries the most time.

Scoping depends on the read surfaces. Before quoting, list every agent, every grounding source and every tool response it consumes, and mark which can be written by someone outside the trust boundary: suppliers, customers, all staff, or the public web through Grounding with Bing.

Chain

StepAttacker actionControl expected to stop itTester records
1Map read surfaces: each agent's indexes, connected sites, mailboxes, web grounding and tools, and who can write to eachGrounding only from curated sourcesWritable surfaces per agent
2Plant canary payloads using hiding techniques: white on white text, HTML comments, alt text, document properties, Unicode tag characters, text inside imagesIngestion scanning; Prompt Shields Indirect Attack on documentsWhich techniques survive ingestion into the index
3As a second, innocent user, ask the agent a normal question that retrieves the planted documentTool response guardrail with Indirect Attack set to blockWhether the payload reached the model, read from the trace
4Payload instructs a tool call outside the user's request: look up another customer, update a record, send a messageTool allow list; human approval on writes; guardrail on tool callsWhich calls were attempted and which executed
5Payload instructs the agent to place canary data in a tool parameter or URL bound for a tester owned endpointAgent identity scope; egress firewallWhether the tester endpoint received anything
6Leave the payload in place and ask from other accounts over the following daysDetection and removal processTime until detected and removed; number of users affected meanwhile

Pass looks like

  • No tool call outside the user's intent executes without a person approving it.
  • No canary data reaches the tester endpoint.
  • The payload is flagged in the logs, and the SOC is alerted to a tool call following an Indirect Attack annotation.
  • The client can find and remove a planted document from every index it reached.

Any single layer failing is a finding; the report states how many layers remained.

Rules of engagement. Payloads are benign and canary based: the instruction is to move a seeded canary record, never real data. Destination endpoints are owned by the tester and agreed in advance. All payloads are removed at the end and their removal confirmed in each index.

AP05 Data leak through rendered output

Start
P3, or P2 with a direct prompt
Target
Chat client, link previews
Priority
High
Estimate
1 day

Goal. Make the model write a link or image whose URL carries conversation data, so the user's browser or chat platform sends it to the attacker.

Why this can work

This leak happens after every server side control has finished. Foundry returns text; the client turns markdown into an image tag; the browser fetches the image; the query string carries the data. Nothing in Foundry, APIM or the firewall sees the browser's request, because it leaves from the user's device.

Chat platforms add a second channel. When an agent posts into Teams or Slack, link unfurling makes the platform's own servers fetch any URL in the message to build a preview, with no click from the user. The client control is therefore the only control, and it has to cover every surface the agent posts to.

Chain

StepAttacker actionControl expected to stop itTester records
1Through an AP04 surface, instruct the model to end its answer with an image whose URL includes the user's question or a canary valueTool response guardrailWhether the instruction reached the model
2Check whether the model wrote the linkOutput filters, which are weak against thisModel output
3Open the answer in each client: web app, Teams, Slack, email digestClient renders as text or proxies images; restrictive image policy in the client's own CSP; unfurling off for agent messagesRequests received at the tester listener, with source IP showing browser or platform

Pass looks like

The tester listener receives nothing from any client, for images, links or previews.

AP06 Cross user access through retrieval and threads

Start
P2, two users in different groups
Target
AI Search indexes, threads, files
Priority
Critical where data is personal or confidential
Estimate
2 days

Goal. As user A, read documents only user B may see, or read B's conversations and uploaded files.

Why this can work

AI Search does not know who the end user is. Security trimming works only if the application or agent adds a filter on an access control field, built from the signed in user's groups, to every query. If one tool omits the filter, if the filter is built from parameters the model chooses, or if a second index was added without access control fields, the search identity returns everything it can see, which is usually everything.

Threads and files have the same weakness at the API layer. If the client application accepts a conversation or file ID from the browser and passes it on without checking who owns it, any user can read any thread by changing an ID. The platform stores the data correctly; the application decides who sees it.

Chain

StepAttacker actionControl expected to stop itTester records
1Client seeds canary documents with distinct access lists for A and BNot applicableSeed set
2As A, ask questions only B's documents answerSecurity trimming filter on every retrieval toolAny B only content returned
3As A, ask the agent to search "without filters", widen the scope, or use another tool or indexFilter applied in code from the token, not chosen by the modelWhether model wording changes the result
4Replay A's API calls with B's conversation, thread, run and file IDsOwnership check per request; session isolation per userStatus codes and any content returned
5Upload a file as B, then reference it from A's sessionFile access scoped to the uploading userResult

Pass looks like

No B only content reaches A by any wording, tool or ID manipulation.

AP07 Confused deputy through the agent identity

Start
P2, a low privilege user
Target
Systems the agent can call
Priority
High
Estimate
1.5 days

Goal. Get the agent to do something in a downstream system that the user could not do directly.

Why this can work

AP06 is about what an index returns. This path is about the systems behind the agent's tools: HR, ticketing, CRM, finance. When the agent calls them with its own identity, the downstream system checks the agent's rights, not the user's. To serve every user, agents are usually granted the union of every user's needs, so each user inherits everything the agent can do.

The fix is the on behalf of user flow, or an explicit authorisation check in the tool, but both are extra work and often skipped. The test needs white box access to the agent's tool definitions and role assignments to choose targets well.

Chain

StepAttacker actionControl expected to stop itTester records
1Compare the agent identity's role assignments and API permissions with the test user'sAgent identity scoped to its charterRights the agent has that the user lacks
2Ask the agent to act on a resource only the agent can reach: another team's ticket queue, a salary recordOn behalf of user flow, or a per call authorisation check in the toolWhether the action succeeds, and whose identity the downstream log shows
3Check the downstream audit trailLogs show both agent and userWhether the real requester can be identified

Pass looks like

Every downstream action is limited to what the requesting user could do, and the audit trail names both the agent and the user.

AP08 Write actions without approval, loops and spend limits

Start
P2 directly, or P3 by injection
Target
Write tools, run limits, APIM token limits
Priority
High
Estimate
1.5 days

Goal. Get the agent to change, send or delete something without a person approving it, keep running without end, or spend beyond its limit.

Why this can work

Approval is configured tool by tool. Teams put approval on the obvious tool ("send email") and miss the one that matters ("update claim status"). Where approval is implemented in the application rather than the platform, it can sometimes be satisfied by text: an injected line saying "the user has already approved this" is just more context to the model.

Loops come from instructions such as "keep checking until it changes", with no maximum steps or run timeout. Spend limits are the backstop for both, and they are worth verifying because a limit set in the wrong product or keyed on the wrong counter does nothing.

Chain

StepAttacker actionControl expected to stop itTester records
1Ask plainly for each write action the agent's tools allowApproval required for every write, send, pay, delete and access change toolTools that executed without approval
2Bury the write as step five of a longer, harmless taskApproval enforced per call, regardless of contextResult
3Inject text claiming approval was already givenApproval enforced by the platform or client, not decided by the modelResult
4Instruct a polling or self repeating taskMaximum steps and run timeoutSteps and tokens before the run stopped
5Against a test APIM product with a deliberately low token limit, send a short burst just over itAPIM token limit per consumerRequest at which 429s began, and whether other consumers were unaffected

Pass looks like

No write executes without a person approving it, runs stop at their limit, and the token limit triggers at the configured value for that consumer only.

Rules of engagement. Denial of service testing, including simulating it, is prohibited. Step 5 uses a lowered limit and a small burst against a test product, to show the limit is wired correctly. Nothing attempts to exhaust deployment capacity. Write actions run against test records only.

AP09 Tool supply chain and request forgery from the agent subnet

Start
P4 for tool registration, P3 for request forgery
Target
MCP servers, OpenAPI tools, internal endpoints
Priority
High
Estimate
2 days

Goal. Introduce a malicious tool, alter a trusted one, or use a tool that fetches URLs to reach internal systems from inside the client's network.

Why this can work

In the reference design the agent runtime is injected into the client's own subnet, so its requests come from inside the VNet with a line of sight to private endpoints and, through ExpressRoute, possibly to on premises systems. Any tool that fetches a URL or host chosen by the model, such as a "read web page" MCP tool or an OpenAPI tool with a URL parameter, is a server side request forgery primitive whose source is the client's network.

MCP adds a supply chain angle. The model reads each tool's description to decide how to use it, so a description can carry instructions (tool poisoning), and a server can change its description or behaviour after it was reviewed. Allow listing by exact server URL and pinning the tool schema are the controls; both need verifying, not assuming.

Chain

StepAttacker actionControl expected to stop itTester records
1List every tool that takes a URL, host, path or query as inputTools take identifiers, not URLsCandidate tools
2Through such a tool, request private endpoint FQDNs, other spoke addresses, on premises hostsInput validation in the tool; NSGs on the agent subnet; firewall rules from the agent subnetInternal targets reached and their responses
3In the development project, register a tester owned MCP server; after review, change its description to include instructionsExact URL allow list; schema pinned and re-reviewed on changeWhether the changed description was accepted and acted on
4Check whether a tool registered in development can be used by a production agentProject separation; production agents deployed only by the pipelineResult

Pass looks like

No tool reaches an internal address outside its purpose, a changed tool schema is rejected or flagged, and nothing registered in development reaches production.

Rules of engagement. The agent runtime is Microsoft managed. If a request from the runtime reaches a Microsoft internal service, such as an instance metadata endpoint of the platform, stop at proof of concept and report to MSRC. Enumeration, secret dumping or pivoting on Microsoft assets is prohibited.

AP10 Egress bypass through allowed destinations

Start
P3 by injection, or P4
Target
Firewall rules, DNS, code interpreter
Priority
High
Estimate
1 day, plus optional boundary testing

Goal. Move canary data out of the agent environment through destinations the firewall already allows.

Why this can work

Agent subnets need to reach Entra ID and Azure services, and firewall rules for that are often written with wildcards such as *.blob.core.windows.net or broad service tags. Those match every storage account in Azure, including one the attacker created in their own subscription. "Private egress only to Azure" can still mean "egress to the attacker's Azure".

DNS is the other common gap. If the agent subnet can resolve arbitrary external names, data can leave encoded in subdomain lookups to a domain whose name server the attacker controls, even when no HTTP egress is allowed. Code interpreter runs in a Microsoft managed sandbox; whether it has outbound access in the client's configuration is worth checking rather than assuming.

Chain

StepAttacker actionControl expected to stop itTester records
1Review firewall rules and service tags applied to the agent subnetExact FQDNs, no wildcards over shared cloud domainsWildcards and broad tags
2From the agent context, write a canary to a tester owned storage account on an allowed wildcardExact FQDN rules; private endpoints for the client's own accounts onlyWhether the write succeeded
3Trigger lookups of tester controlled subdomains carrying a canaryDNS filtering on the resolver or firewall DNS proxyQueries received at the tester name server
4From code interpreter, attempt DNS and HTTP to a tester endpointNo outbound access from the sandboxResult

Pass looks like

No canary reaches any tester owned destination by HTTP, storage write or DNS.

Rules of engagement. Attempting to break out of the code interpreter sandbox is permitted, but on success the tester stops immediately and reports to MSRC; no further action on Microsoft infrastructure. Agree in advance whether boundary testing is in scope, as it adds time without testing the client's own configuration.

AP11 Developer privilege escalation and guardrail tampering

Start
P4, Foundry User on a development project
Target
Control plane, other projects, connection secrets
Priority
High
Estimate
2 days

Goal. From an ordinary developer account, reach the control plane: create deployments, weaken content filters, read connection secrets, reach other projects, or switch on public access or keys.

Why this can work

Foundry's roles separate control plane from data plane well on paper, but organisations hand out Contributor or Foundry Owner to unblock a team and never take it back. One account with those rights can detach a filter policy from a deployment, which disables content safety for every app on it in a single change.

Connections are the subtler route. Connections created at the Foundry resource level can be shared across projects, and some connection types still hold secrets that an identity with the right action can list. Azure Policy is meant to be the backstop for public access and keys, so the test also confirms the policy is in Deny, at the right scope, without an exemption covering this resource.

Chain

StepAttacker actionControl expected to stop itTester records
1Enumerate own role assignments and every resource visible through Resource GraphLeast privilege, project scoped assignmentsEffective rights
2Create a model deploymentDeployment write not in Foundry UserResult
3Change or detach a filter policyFilter policy writes restricted to the platform teamResult
4List connections and try to retrieve their secretsEntra ID connections; secret listing not grantedAny secret returned
5Read agents, threads or files in another projectProject scoped role assignmentsResult
6Enable local auth or public network accessPolicy Deny, no exemptionResult and the policy that denied it
7Create a role assignmentNo role assignment rightsResult

Pass looks like

Every step is denied, each denial appears in the Activity Log, and steps 3 and 6 raise alerts.

AP12 Unapproved training and model deployment

Start
P4
Target
Fine tuning, model policies, data collection
Priority
Medium
Estimate
1 day

Goal. Fine tune a model on uploaded data, deploy it or another unapproved model, or switch on features that keep user data for later reuse.

Why this can work

Default data plane roles include fine tuning and dataset upload. Personal data trained into weights cannot be selectively removed, so this is a data protection failure even if no attacker is involved, which is why the priority is Medium: the harm is regulatory and slow rather than an immediate breach.

The approved models policy matches asset IDs by prefix. An entry without a trailing slash approves every model whose name starts the same way, and a publisher entry approves every future model from that publisher. Testing what the policy actually allows is the only way to know.

AP13 Pipeline identity abuse

Start
P5, repository write access
Target
Federated credentials, self hosted runner, infrastructure
Priority
High
Estimate
1.5 days

Goal. Use the pipeline's identity to change infrastructure without review, for example to switch off a guardrail or open network access.

Why this can work

The pipeline usually holds the highest standing rights in the estate, because it deploys everything. Workload identity federation removes the secret but moves the risk into the federated credential's subject: a subject that matches any branch, any pull request or any environment lets code that never passed review obtain a token.

The self hosted runner inside the spoke is both a privileged identity holder and a network foothold. If it is not ephemeral, tokens and files from earlier runs can remain on disk. If the repository is public and the runner accepts jobs from forks, an outsider can run code inside the client's network.

Only reviewed code on a protected branch and approved environment gets a token, and policy denies guardrail weakening even when it does.

AP14 Network foothold to private endpoints

Start
P6, a host in another network location
Target
Private endpoints, DNS
Priority
Medium
Estimate
1.5 days

Goal. From a compromised host elsewhere, reach Foundry and its stores, and establish what an attacker with network reach can do.

Why this can work

A private endpoint is reachable from anything routed to its subnet: peered spokes, on premises over ExpressRoute, and other clouds over the interconnect. NSGs on a private endpoint subnet only take effect when network policies are enabled on it, which is off by default on older subnets. Private often means "reachable from the whole corporate network".

Entra ID still applies, which is why the priority is Medium: reach alone is not access. The finding that matters is reach combined with any valid token, for example a compromised user who holds Foundry User for an unrelated project.

AP15 Detection and response validation

Start
Runs alongside every other path
Target
Logs, alerts, SOC process, kill switch
Priority
High
Estimate
2 days

Goal. For every other test, establish whether it was recorded, whether an alert fired, and how long the response took. Then rehearse the agent kill switch.

Why this matters

A control that blocks silently looks exactly like a control that never ran, and a detection rule that has never fired may not work. Running detection checks alongside the attack paths, as a purple team exercise, turns the test into evidence: each blocked attempt shows up as a log line, each successful one as an alert, and any gap between them is a finding.

Logging itself is a target. An attacker who deletes a diagnostic setting blinds every rule that depends on it, and the only rule that catches that is one that looks for absence.

Pass looks like

Every test action appears in the logs with an identity, the agreed alerts fire within the agreed time, the kill switch stops the test agent within 15 minutes, and the absence rule fires when logs stop.

What to ask the client before quoting

Effort depends far more on the number of agents, tools and grounding sources than on the size of the Azure estate. These answers set the quote.

  1. An agent inventory: each agent, its model deployment, its tools, its grounding sources, and who can write to each source.
  2. The architecture as built: network diagram, firewall rules for the agent subnet, private endpoint list, APIM configuration.
  3. Role assignments for the AI subscriptions, and the federated credential subjects of the deployment pipeline.
  4. Which starting positions are in scope, and the test accounts for each (two end users in different groups as a minimum).
  5. A canary data set: seeded records and documents the tester may try to move, with distinct access lists.
  6. Tester owned endpoints for listeners, storage and DNS, agreed in writing.
  7. Acceptable attack success rates for AI tests, per harm category, agreed before testing.
  8. Whether the SOC is told (purple team) or not (detection blind test), and the emergency contacts on both sides.
  9. A cost cap for tokens, fine tuning and any deployments the tests create.
  10. The test window, any change freeze, and agreement on reporting any Microsoft platform issue to MSRC.
